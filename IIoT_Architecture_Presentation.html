1. 傳統機台連線的痛點

💥

孤島與瓶頸

  • 資料孤島各廠牌 PLC (Beckhoff, Siemens) 協定不通，廠內難以橫向整合，資料難以上雲。
  • 資安開洞傳統架構要求 IT 防火牆「雙向開洞」讓外部讀取機台，造成嚴重資安漏洞，被駭客入侵風險極高。
  • 資料庫崩潰工業感測器資料量龐大，寫入傳統 SQL (關聯式資料庫) 容易導致索引碎片化與效能卡死。

3. 第一層：現場設備 (OT Source)

⚙️

OPC UA Server

  • 工業標準通訊 OPC UA 已經是 OT 領域的主流通訊協定，打破了以往各家硬體廠商各自為政的封閉通訊。
  • 單一對外端口 機台 (如 Beckhoff PLC) 扮演 Server。即使機台下接了 4 個 Channel 感測裝置，對外也只需要開放單一個 OPC UA IP 連線。擷取端透過訂閱精確的 Node ID 來獲取指定通道數據。

4. OPC UA 的雙面刃

⚖️

優勢 vs 包袱

  • 優點：絕對嚴謹的結構 不僅傳輸數值，還夾帶了豐富的屬性 (資料型別、單位、時間戳記、品質標籤)，這保證了廠內溝通的一致性，不會有數值定義不清的問題。
  • 缺點：厚重難上雲 龐大的封包極度消耗網路頻寬。更致命的是，傳統 Server/Client 模式需要外網主動連入 (雙向連線)，完全無法直接穿越現代嚴密的企業防火牆。

5. OPC UA 實務踩坑點

🛡️

連線地雷

  • X.509 憑證交換 安全連線的第一道門檻。Client (Node-RED) 與 Server (PLC) 必須互相信任彼此的 X.509 憑證，未授權的設備絕對連不上，也是最常連線失敗的原因。
  • 時間戳記之謎 (Timestamp) 必須嚴格區分 Source Timestamp (感測器產生數據的時間) 與 Server Timestamp (PLC 內部收到的時間)。務必確保 NTP 時鐘同步，否則寫入時序庫會造成報表錯亂。

6. 第二層：邊緣擷取層 (Edge 中樞)

🧠

資料洗石機

  • 資料剝殼 (Payload 瘦身) 邊緣電腦負責將 OPC UA 龐雜的肥大封包剝開，拋棄不必要的 metadata，只萃取出核心的物理數值。
  • 轉譯 JSON 將厚重資料轉換成輕薄短小的標準 Web 格式：
    {"machine":"M1", "temp": 25.4, "time": "14:00"}
  • 協議轉換橋樑 做為 OPC UA 的 Client (向內抓取) 同時扮演 MQTT 的 Publisher (向外發布)，完美隔離 OT 與 IT 網路。

7. 邊緣運算：邏輯分流實戰

🔀

Node-RED 首選

  • 為何首選 Node-RED？ 比起純粹搬運資料的 Telegraf，Node-RED 的強項在於它是「邏輯中樞」，它具備 Low-code 視覺化介面，讓工程師能輕易刻畫商業邏輯。
  • 異常觸發自動化 (Ragic API) 資料正常打上雲端的同時，Node-RED 可並行判斷 數值 > 80度。一旦超標，便即時觸發 HTTP Request，打 API 到 Ragic 自動建立一張「機台異常保修單」。

8. 第三層：雲端傳輸 MQTT

📡

Pub/Sub 解耦

  • 廣播頻道概念 發布者與訂閱者互不相識。Edge 發布資料到特定 Topic，不管誰在聽；Grafana / DB 訂閱 Topic，不管誰在發。系統新增節點時不需修改舊有架構。
  • 主動推播 (Push) 徹底淘汰傳統效率低落的「輪詢 (Polling)」。只要機台數值一有變化，MQTT 立即主動推播給所有訂閱者，達到毫秒級的極致低延遲。

9. MQTT 的資安與效能絕對優勢

🧱

防火牆穿透

  • 單向對外 (資安防護罩) 廠內設備只需對外 (通常是 Port 8883) 建立「單向 TCP 連線」推播數據。IT 防火牆完全不需要開放外部連入廠內，徹底解決傳統工廠資安抗性。
  • 極度省頻寬 MQTT 的控制封包 Header 最小僅 2 bytes，專為不穩定、低頻寬的 IoT 網路設計。傳輸 JSON 的負載極輕，有效控制網路流量成本。

10. MQTT Broker 選擇指南 (地端篇)

🖥️

資料不出廠

  • Mosquitto (最經典開源) 全世界最普及的輕量級 Broker。透過 Docker docker run -p 1883:1883 一秒架設完成，免憑證煩惱，適合嚴格限制外網的封閉廠區。
  • EMQX (企業級開源) 專為現代高併發設計，一樣可 Docker 部署，內建極度華麗的 Web 儀表板，可讓網管人員直接在瀏覽器監控百萬級設備的連線狀態與網路吞吐量。

11. MQTT Broker 選擇指南 (雲端篇)

☁️

公有雲擴充

  • AWS IoT Core / Azure 無縫銜接雲端大數據與機器學習 (ML) 算力。資安極其嚴格，必須在 Node-RED 匯入完整的 X.509 憑證套件 (憑證, 私鑰, Root CA) 並透過 MQTTS 通訊。
  • HiveMQ Cloud (BaaS) 免養伺服器、不用搞懂 AWS IAM 權限。註冊即用專屬 URL 與帳密連線，極度適合新創專案或概念驗證 (POC)，做到零 IT 包袱。

12. 第四層：儲存層 (Consume - DB)

🗄️

為何選 InfluxDB

  • 拒絕關聯式 SQL 機台溫度、壓力數據是「只新增、不修改、頻率極高」的資料流。若用 MySQL 處理每秒寫入，很快就會發生硬碟 IO 瓶頸與索引崩潰。
  • TSDB 寫入極限 InfluxDB (時序資料庫) 專為 Timestamp + Value 結構深度優化，支援每秒數萬筆的超高速寫入，並提供專門針對時間範圍的聚合查詢語法。

13. InfluxDB 資料保留策略 (RP)

🗜️

自動降維壓縮

  • 硬碟防爆機制 若 24 小時永久保留所有機台的每秒原始數據，昂貴的 SSD 儲存空間將在幾個月內耗盡。InfluxDB 內建了優雅的 Retention Policy。
  • 實務作法 (Downsampling) 設定 RP：讓「秒級原始高頻資料」自動銷毀，只保留 7 天。
    搭配 Continuous Query 在背景自動將資料壓縮成「每小時平均值 / 最大值」，這些壓縮後的報表資料則永久保留做為歷史趨勢分析。

14. 第五層：視覺化與警報 (Consume - Viz)

📊

實時戰情室

  • 與 Power BI 的定位差異 Ragic 搭配 Power BI 是看「歷史營運報表」。InfluxDB 搭配 Grafana 則是看「實時機台心跳與毫秒波動」。Grafana 不存資料，專注於高速渲染波形圖。
  • 強大的警報引擎 (Alerting) 可以設定動態的聚合閾值 (例如：過去 5 分鐘平均壓力低於 30 bar)。一旦超標，立刻透過 Webhook 將截圖與警報打到 LINE Notify 或是 Slack 群組。
